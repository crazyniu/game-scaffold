# 05 开发规范

## 1. 代码（TypeScript，Cocos 版 `client/`）

- **严格模式**：`tsconfig` 开 `strict`、`noUnusedLocals`；不用 `any`，JSON 取值收窄成具体类型。
- 命名：文件与变量 `camelCase`，类与类型 `PascalCase`，常量 `UPPER_SNAKE`；页面类叫 `XxxPage`。
- `core/` 内：**不 import `cc`**；不碰时间、存储、`Math.random`。时间由调用方传入，随机数由传入的 `Rng` 提供。
- 界面层（`ui/`、`game/`、`pages/`）只做表现与输入转发，不写规则判断；规则一律调 `core/`。单个文件超过 400 行就考虑拆。
- 界面全部由代码生成（`ui/kit.ts` 的 `box`、`img`、`slice`、`text`、`button`…），不用编辑器拖 prefab。点击用 `onTap`（自带按下缩放、滑动不算点）。
- 异步回调里访问节点前先查 `node.isValid`；页面重建时先停掉挂在旧节点上的缓动。
- **Cocos 构建的坑（`./run.sh check` 都有检查）**：不写 `as X | Y`（用小函数收窄）；不展开 `Map` / `Set` / 迭代器（用 `Array.from`）；`resources.load` 成功时 `err` 是 `undefined`，判断用 `if (err)`。
- 注释只写「为什么」，用中文。不提前抽象：同样的代码出现第三次再提取。

## 2. 配置与文案

- 数值全部进 `client/assets/resources/config/`，代码通过 `App.config` 读取，不写魔法数字。
- 玩家可见文字全部走 `tr('KEY')`，key 形如 `UI_HOME_START`，翻译在 `i18n/strings.csv`（每种语言一列，都要填；改完 `node client/tools/i18n.mjs` 生成 `strings.json`，再 `./run.sh font-subset`）。卡名、章节名也走文案（`CARD_<ID>`、`CHAPTER_<序号>`）。
- 带文字的美术图（如标题字）出中英两版，或改用字体渲染。

## 3. 测试：只测值得测的

原则：测试是为了防止规则算错和关卡不可解，不是为了数量或覆盖率。

**要写**

| 范围 | 内容 |
|---|---|
| 玩法规则（`core/<玩法>/rules.ts`） | 每条规则、每种障碍、每个道具各有少量用例，重点是连锁结算与胜负边界 |
| 关卡生成 | 同种子输出一致；全部关卡按参考解能过 |
| 外围系统（`core/meta`） | 每个系统几条主路径；数值从 `economy.json` 读，不写死在测试里 |
| 配置对齐 | 每个技能、卡、章节、任务都有图和文案（`client/tests/config.test.ts`） |
| 存档迁移 | 每个迁移函数一个用例 |
| 回归 | 修规则类 bug 时补一个能复现它的用例 |

**不写**

- 界面、动画、场景、`services`、`platform` 的单元测试。
  这些靠在 Mac 上实际跑和验收。
- 只是转发调用、读配置、取值赋值的代码的测试。
- 覆盖率指标、快照测试、端到端自动化、为了测试而加的抽象层与 mock。
- 同一逻辑的重复用例：一个行为一个用例，边界值各一个，够了。

整套单测本地运行应在 30 秒内跑完，超过就删慢的、合并重复的。

## 4. CI（GitHub Actions）：一条流水线，三分钟内

只在 **向 `main` 提 PR** 时触发，一个 job，顺序执行：

1. `./run.sh check`：`.meta` 与图片压缩检查、存档前缀和 `codeName` 一致、Cocos 构建坑的几条 grep 检查、类型检查（核心与工具；界面层要 Cocos 的类型声明 `client/.cc-types/`，CI 上没有，只在本地查）、`core/` 的单测
2. `./run.sh level-verify`：全部关卡按参考解能过

**CI 里不做**：

- 不在每次 push 都跑；不设定时任务。
- 不做多平台导出构建矩阵、不跑真机或模拟器、不跑界面自动化。
- 不卡覆盖率。关卡校验只有「可解」不过才算失败；难度偏离目标只进报告，不拦 PR。
- 不新增 job。要加检查项，先证明它拦得住真实出现过的问题，并且总时长仍在三分钟内。

发版导出（三端构建）是手动触发的独立 workflow，不属于 CI。

## 5. 项目管理（GitHub）

仓库：每款游戏一个（从底座 clone 出来的新仓库，`docs/00` 第 0 步）。

- **Milestones**：对应 `docs/07` 的 M0–M6。
- **Issues**：一件可独立验收的事一个 issue，用仓库里的模板（功能 / 缺陷 / 美术需求）。美术需求 issue 就是给 Codex 的 brief 的索引。
- **Labels**：`core` `game` `ui` `platform` `level` `art` `docs` 表示范围；`bug` `feat` `chore` 表示类型；`wechat` `android` `ios` 表示平台；`blocked` 表示等用户或等资质。
- **Project 看板**：Todo → Doing → 待验收 → Done。「待验收」是等用户看界面或美术的状态。
- **分支与 PR**：`main` 受保护、始终可运行；功能在 `feat/简述`、修复在 `fix/简述`；一个 PR 关联一个 issue（`Closes #n`），CI 通过后 squash 合并。
- **提交信息**：`类型(范围): 说明`，类型取 `feat / fix / refactor / docs / test / chore / art / level`，说明用中文。例：`feat(core): 冰冻块结算`。
- **Releases**：每次提审打 tag `v主.次.修`，Release 说明里写三端各自的构建号。
- 规则变更的文档与代码放同一个 PR。
- 不提交：`client/library`、`client/temp`、`client/build` 等 Cocos 缓存与构建产物、`client/node_modules`、`client/.cc-types/`、`art/raw/`、任何密钥与签名文件。资源的 `.meta` 要提交（由 `./run.sh meta` 生成）。

## 6. 性能预算（以三四年前的中低端安卓机为准）

| 指标 | 预算 |
|---|---|
| 帧率 | 局内稳定 60，最低不低于 45 |
| Draw Call | 局内 ≤ 40，其它界面 ≤ 60 |
| 冷启动到可点击 | 小游戏与 Android 的目标值在 M0 验证后定 |
| 同屏元素 | 玩法最多的那一关不掉帧 |

一闪而过、源源不断的特效小图（火花、水波、彩纸、冒泡）走对象池（`kit.fxImg` / `recycleFx`）；局内每帧的 `update` 里不做分配；看不见的东西（透明度 0、压扁成 0）直接隐藏，不让它画。

量绘制调用的办法：页面里按渲染顺序走一遍节点、数贴图切换次数，和引擎的 `numDrawCalls` 基本一致。只做不伤画质的优化（mipmap 和动态合图不兼容、预打图集用不上调色板压缩、纹理压缩有损，这几样都不做）。

## 7. 广告与埋点

- 激励视频统一经 `ui/popups.ts` 的 `watchAd(广告位)`；插屏频控读 `ads.json`（`core/meta/meta.ts` 的 `shouldShowInterstitial`）。业务代码不直接调平台实现。
- 激励视频只有返回 `done` 才发奖；`unavailable` 时给出提示且不扣次数。
- 埋点走 `App.platform.track`；每个广告位、每关的开始 / 胜利 / 失败 / 复活 / 道具使用的埋点在接真实平台时补齐（现在只有广告看完）。

## 8. 完成标准

1. 对应文档已更新。
2. CI 通过。
3. 在编辑器里实际跑过相关流程。
4. 涉及平台能力的，在对应平台开发者工具或真机验证过；没验证的在 PR 说明里明写「未在 X 平台验证」。
5. 没有新增魔法数字、硬编码文案、跨层调用。

## 9. 开发机与测试机分工

- **Linux 开发机（AI 所在）**：只写代码、配置、文档、关卡工具，跑 Node 的检查与单测（`./run.sh check`、`./run.sh level-verify`、`./run.sh eco-sim`），做 `git` 操作。需要 Cocos Creator 的事（构建、试玩、截图、界面验收、打包）不在这台机器上做。
- **Mac 测试机（装了 Cocos Creator 3.8.8、Xcode、Android Studio）**：构建、试玩、截图、打包都在这里。用户的环境里它是 Orca 环境 `Mac-Image-Worker`，AI 用 `orca` CLI 驱动，不需要用户手动操作；新游戏的仓库要先在 Mac 上 clone，并 `orca repo add --environment Mac-Image-Worker --path <Mac 上的仓库路径>` 登记（第一次问用户放哪）。
- **同步只走 git**：Linux 上提交并推送，Mac 上 `git checkout -- client && git pull --ff-only`（Cocos 构建会改写 `.meta`，先还原）。`./run.sh` 的试玩、`serve`、`editor` 运行前会自动做这一步（`NO_PULL=1` 跳过）。未推送的改动 Mac 看不到。
- **在 Mac 上试玩**：
  1. 开终端跑：`orca terminal create --environment Mac-Image-Worker --worktree "path:<Mac 上的仓库路径>" --title <名称> --command 'cd <仓库路径> && ./run.sh level 5' --json`，记下 `handle`。`./run.sh` 构建网页版、起本地服务，用独立的 Chrome 窗口打开（单独的用户目录 `<代号>-chrome`，不碰用户自己的 Chrome；两款游戏同时试玩时端口会自动错开（`WEB_PORT`、`CDP_PORT` 也能手动指定））。
  2. 读输出：`orca terminal read --environment Mac-Image-Worker --terminal <handle>`，看到「Ctrl+C 停止」就开好了。
  3. 截图、求值：`./run.sh cdp shot <文件>`、`cdp eval '<表达式>'`、`cdp burst <目录> <张数> <间隔毫秒>`（窗口被挡住也能截）；`cdp logs` 读控制台（会重新加载页面）；`cdp watch` 盯卡死。也可以 `orca computer get-app-state --app pid:<Chrome 的 pid>` 截窗口、`orca computer click` 点（坐标 = 截图坐标 ÷ scale）。
  4. 收尾：关掉自己开的终端（`orca terminal close`），按进程号结束那个 Chrome，不留后台进程。
- **交给用户测**：Mac 上 `./run.sh lan`，把打印的内网地址发给用户；服务留着，用户说测完再关。
- **只读优先**：在 Mac 上除 git 同步、`./run.sh`、`./package.sh` 外不改文件、不装软件、不碰别的项目。
- **验收口径**：第 8 节「在编辑器里实际跑过」指在 Mac 上跑过。PR 说明里写清楚在 Mac 上测了什么，没测的明写「未在 Mac 上验证」。
